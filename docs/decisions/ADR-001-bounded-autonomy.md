# ADR-001：无人看守采用有界自治

- 状态：已接受
- 日期：2026-10-18

## 背景

产品定位是无人看守执行。现有普通派活可以长时间等待选手进程，只在界面提示“较久没有新动作”；验收命令有超时，但选手执行没有统一的无动作与总时长上限。小队可按轮审改，但不会自动诊断停滞或把过大任务拆成可验收的子任务。

## 决定

1. 无人看守是“有界自治”：每次选手执行、恢复、诊断、审查、验收都必须同时受无动作时限、单次总时限和整体预算限制；不做无限重试。
2. 停滞不等于失败。平台先安全停掉进程树，保存日志、活动、改动、验收结果和进程原因，再由负责人 AI 在新会话中分类为续跑、重试、细拆、已完成可转验收或需要主人。
3. 负责人 AI 输出是不可信数据。核心只接受严格白名单的动作和有长度边界的纯文本题目，不执行 AI 生成的 shell 命令、路径、选手或权限。
4. 自动细拆不直接改写项目的 `docs/TASK_LIST.md` 和 Task Spec。子任务是自治执行记录里的有向无环图，最大深度、节点数和总尝试数由主人的策略限制。
5. 一次自治执行使用平台创建的专用副本，子任务串行写入。每个通过审查的节点形成平台管理的累积补丁快照；恢复时只能回到上一个已接受快照，不碰主工作区。
6. 自动审查与验收必须独立于写手。平台只运行项目已登记的验收命令，不运行负责人 AI 或写手临时提议的命令。
7. 只有安全/登录/额度拦截、整体预算用完、恢复方案无法通过核心校验、重复循环或没有可登记验收的安全下一步时，才转为“需要主人”。

## 影响

- 普通任务看管会新增可配置执行预算和明确的超时结果。
- 自治执行不复用普通批次表达全局状态，而是有自己的原子登记文件和后台推进器。
- 自动细拆初版必须串行；未证明不会冲突前不开放并行写。
- 系统会更早停下已无进展的选手，但对长时间的正常命令必须依据“无活动 + 日志无增长 + 宽限期”而不是单看界面动作。
