# TASK-013：需要主人事件与飞书可靠投递底座

- 状态：`DRAFT`
- 优先级：`P1`
- 难度等级：`High`
- 前置任务：`TASK-010` 评审为 `PASSED` 或 `PASSED_WITH_NOTES`
- 需求来源：无人看守进入求助或等待主人决定时，除应用内历史外，还要通过飞书机器人主动通知主人；负责人 AI 不可用时也不能静默。

## 业务结果

无人看守流程一旦真正需要主人处理，平台会先留下可审计的通知事件，并在不依赖任何 AI 调用的情况下通过已连接的飞书群机器人有界投递；发送失败不影响任务收尾，也不会丢失或无限重试。

## 范围

- 包含：结构化通知事件、持久待发队列、去重、固定消息模板、飞书 Webhook 主机/路径校验、签名、超时、有限退避、成功/失败记录、应用启动和运行中的消费、离线后补发、核心与主进程测试。
- 包含：`owner`、负责人 AI 不可用、恢复预算用尽、循环被挡及其他 `needs_owner` 原因的事件映射。
- 不包含：设置页输入与连接测试界面、飞书反向回复/审批、交互卡片、企业应用机器人私聊、普通进度或成功完成通知。

## 现状与设计

- 现有 `app/main/notifications.ts` 只在桌面应用运行时发系统通知，使用按 View 推导的去重记录；没有跨渠道待发状态，也没有失败重试证据。
- TASK-010 必须在状态落为 `needs_owner` 的同一次受锁状态变更中追加稳定事件 ID。事件正文不是负责人 AI 输出，而是由原因码和受限展示字段生成；写事件失败时不得把状态假装写成功。
- 新的通知账本位于登记处，只保存非敏感事件、尝试次数、下次尝试时间、送达时间和脱敏错误；写入仍遵守“锁内读改写、临时文件改名”。Webhook 与签名密钥不在账本中。
- 投递器从凭据适配器取得凭据，严格限制 HTTPS、飞书官方 Webhook 主机和固定路径，不跟随重定向；请求和响应均有大小、时长上限。响应只有明确成功才标记送达。
- 同一事件成功一次后永不重发；进程在请求完成、账本落盘前退出时，允许飞书端收到一次重复消息，因此正文携带短事件号，测试并记录这一“至少一次”边界。
- 退避必须有上限；达到单次启动尝试上限后停止本轮，等待定时器、设置保存、网络恢复或下次启动重新唤醒。不得占用负责人 AI 或选手预算。

## 约束

- 遵守 `AGENTS.md` 与 ADR-003；不新增依赖。
- 任何模型输出、日志、diff、环境变量、绝对路径、原始异常栈和密钥都不得进入飞书正文。
- 飞书发送失败不能回滚或覆盖 `needs_owner`，也不能阻止停止选手和进程树。
- 选手联网总开关不控制平台通知；投递器只能访问主人保存并通过白名单校验的飞书 Webhook。
- 自动测试完全离线，以注入的请求函数、时钟和凭据适配器验证行为。

## 验收标准

1. TASK-010 的全部 `owner`/负责人不可用分支以及预算耗尽、循环拦截分支，各自只生成一个稳定、可审计的通知事件；重复推进不增加重复事件。
2. 未配置飞书时事件仍保留且界面历史不受影响；后来完成配置后可投递尚未过期的待发事件，但不补发主人已在应用内处理完的事件。
3. 负责人 AI 报“额度已用完”、启动前额度检查拒绝、诊断超时/崩溃/非法输出时，不再调用另一个 AI，仍产生并投递固定模板通知。
4. 官方主机外地址、HTTP、重定向、超长字段和异常响应在请求前或标记成功前被拒绝；账本和错误摘要中找不到 Webhook token、签名密钥和绝对路径。
5. 网络错误、429、5xx 和进程重启按上限退避并可恢复；明确 4xx 配置错误暂停自动重试并留下“需要检查连接”的脱敏状态；任何情况都没有无限定时器或活进程。
6. 明确成功后相同事件不再发送；请求成功但成功账本未落盘的崩溃窗口以短事件号可识别，并有测试覆盖。
