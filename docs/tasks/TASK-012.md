# TASK-012：无人看守控制台与恢复证据展示

- 状态：`PASSED`
- 优先级：`P2`
- 难度等级：`Medium`
- 前置任务：`TASK-011`、`TASK-013` 评审为 `PASSED` 或 `PASSED_WITH_NOTES`
- 需求来源：无人看守流程需要可启动、可查看、可停止，并在真正需要主人时给出清楚证据。

## 业务结果

主人可在规划页对一个可执行任务开启无人看守，明确选择写手/审查范围和预算；之后可看到当前阶段、细拆步骤、自动恢复原因、剩余预算与最终验收，并可随时停止。

## 范围

- 包含：界面规范，主进程/preload 白名单桥，启动确认弹窗，预算选择，自治执行列表/详情，子任务图和诊断/验收证据，停止，`needs_owner` 明确提示，界面与真窗口测试。
- 不包含：修改核心自治策略、无确认自动开启全部 READY 任务、自动合并主分支。

## 现状与设计

- 先更新 `docs/ui-spec.md`。规划页的普通“派发”与“无人看守”明确分开；无人看守弹窗必须显式选择写手、审查者、强度、权限、网络快照以及预设预算，不根据 Task Spec 推荐自动选人。
- 界面只传项目标识、Task ID、已选 roster 选项和预设编号；不传 repo/worktree/spec 绝对路径、命令、隔离配置或自定义预算 JSON。后台重新读权威规划和设置。
- 详情页按时间线展示平台事实：阶段、节点、选手尝试、停滞/超时、负责人决定、审查、验收和剩余预算。不显示“可能卡住”之类猜测，只显示已记录原因。
- `needs_owner` 卡片用明确原因和“需要决定”置顶；本任务只提供停止与查看证据，不新增绕过预算/安全检查的“继续”按钮。
- 详情时间线显示“已排队通知 / 已送达 / 发送失败待重试 / 连接需检查”等脱敏事实，但不展示 Webhook、签名、响应原文或重试内部细节；飞书失败不改变自治执行本身的最终状态。

## 验收标准

1. 只有真正可执行的 READY 任务显示无人看守入口；选择不完整、非法预设或非 roster 选手不能提交。
2. 弹窗成功启动后显示自治执行号；重复点击和同 Task 并发请求不会创建重复执行。
3. 详情可稳定显示所有核心状态、子任务依赖、恢复原因、审查/验收结果和剩余预算；旧记录缺少新字段时不崩溃。
4. 停止按钮能停止推进器、当前选手及其进程树，且记录为主人停止；不留存活进程。
5. `needs_owner` 在看板与详情均有明确、不靠颜色的可访问提示；正常自动恢复不会频繁骚扰主人。
6. 浅色、深色、窄窗口和启动弹窗截图通过，真窗口冒烟覆盖启动、查看、转 `needs_owner` 和停止。
7. `needs_owner` 的通知投递状态可见且与 TASK-013 账本一致；未配置飞书、离线和旧记录缺字段时页面不崩溃，也不把“未送达”误写成自治执行失败。
