## 业务结果

每次执行结果、失败和验收证据都回到唯一受信负责人通道复审，再由负责人决定通过、增量修正、换人、拆分或求助，效果近似人工复制执行合同与报告。

## 非目标

- 不让执行者自行决定恢复策略或改写规划事实。
- 不把完整任务历史、主人会话或未受限日志交给执行者。
- 不在本任务实现换人顺序、并行队列或新能力评分。
- 桌面显式入口、增量制品落入新 Git 起点后的授权续跑分别验收；本任务只交付显式运行协议，不声称完全无人看守。

## 架构设计

平台构造可定界的负责人证据包：当前 Capsule、Implementation Report、diff 摘要、结构化活动、验证结果和剩余预算。负责人回包只允许固定动作；修正和拆分必须生成新的增量 Capsule，不把自由文本变成命令或配置。负责人身份由受信适配层固定，不从项目或执行者输入接收。

运行记录必须绑定协议版本、原胶囊快照/指纹、候选补丁哈希、动作令牌及生成制品指纹；决定和整组胶囊引用须原子保存，恢复时先核对原身份和制品，不按当前设置猜测或重放。现有独立 reviewer 选择不能直接冒充受信负责人。旧记录保持原语义，不静默解释为新协议；存储与恢复切片完成后再切运行状态机。

## 兼容要求

- 旧登记、动作令牌和诊断记录保持可读，缺新字段时不猜测或重放。
- Capsule 和 Review Record 契约不嵌入供应商信息。

## 验收标准

1. 完成、失败、验收失败和主动中断均先进入负责人复审。
2. 负责人只能返回 `accept | correct | handoff | split | owner`；越界动作在副作前被拒绝。
3. `correct` 和 `split` 只产生经契约校验的增量 Capsule。
4. 负责人不可用、额度被拒、回包不合法或超预算时，有界进入 `needs_owner`，不换执行者冒充负责人。
5. 端到端替身测试证明自动信息边界与人工复制粘贴一致。

## 依赖与排序

- TASK-025 先确保执行者直接消费当前 Capsule。
- TASK-039 先提供有界证据包与严格五动作提案解析；本任务只在该底座通过后接运行侧，不重复实现协议或将提案直接用作提示词。
- TASK-040 将提案编译为继承原边界并通过共享校验的增量胶囊；本任务负责制品的原子持久化、负责人身份与恢复接线。

## 主要接口

- `src/core/lead-review.ts` — 负责人证据包和五动作提案协议。
- `src/core/lead-capsule.ts` — 原边界继承和内存共享契约验证。
- `src/core/autopilot.ts` — 版本化运行身份与原子决定/制品引用。
- `src/core/autopilot-engine.ts` — 负责人复审状态转移。
- `src/core/workers.ts` — 受信负责人适配层。

## 长期约束

- 负责人与执行者是可区分角色，两者输出均是不可信文本。
- 自动修正和拆分仍受尝试、时长、节点和用量预算约束。
- 增量制品不得绕过 TASK-025 的起点与锚点核验；没有提交授权时不能为满足起点检查偷偷提交代码。
